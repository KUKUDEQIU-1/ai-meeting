# AI 会议任务自动化工具开发交付文档

## 1. 文档目的

本文用于说明 AI 会议任务自动化工具的整体功能、适用场景、通用能力、已交付模块、人工处理耗时对比、自动化节省时间估算，以及后续 Agent / Skill / Worker 迭代时必须补充的文档规范。

后续每次新增 Agent、Skill、Worker、自动化脚本或有效交付功能，都应在本文继续补充，避免只交付代码、不沉淀使用说明和业务价值。

## 2. 工具定位

AI 会议任务自动化工具不是单纯的会议纪要摘要工具，而是一个把会议内容转成正式任务闭环的自动化系统。

核心链路：

```text
会议内容来源
  -> 自动读取原文
  -> AI 提取摘要、任务、进展和证据
  -> 过滤无效任务并合并重复任务
  -> 匹配负责人、历史任务和团队记忆
  -> 生成待确认草稿
  -> 飞书交互卡片发送给负责人或统筹人
  -> 人工确认、修改、分配、丢弃
  -> 写入正式任务总表
  -> 后续任务巡检和进展更新
```

## 3. 当前已交付范围

### 3.1 会议内容来源

当前支持以下来源：

- 飞书 Wiki / docx 会议原文目录。
- GetNote 笔记。
- 手动输入会议文本。
- 历史飞书会议纪要兼容链路。

主要生产链路是飞书 Wiki / docx 自动扫描；GetNote 作为备用会议来源和评审演示来源。

### 3.2 AI 分析能力

系统可以从会议原文中提取：

- 会议标题。
- 会议摘要。
- 今日新增任务。
- 旧任务进展。
- 可执行证据。
- 负责人候选。
- 任务说明和上下文。
- 无效事项或讨论项。

### 3.3 任务质量控制

系统已具备以下任务质量控制能力：

- 过滤泛泛而谈的“今日工作”“继续看一下”等无效任务。
- 将“已完成、继续推进、已有进展”识别为旧任务进展，而不是新任务。
- 通过任务名称、任务说明和语义相似度合并重复任务。
- 对缺少明确执行动作、缺少业务对象、缺少证据的事项降权或移除。
- 保留 AI 明确判断为可执行但规则低分的任务，进入人工确认。
- 记录候选任务审计信息，方便排查为什么被保留或过滤。

### 3.4 负责人归属和成员记忆

系统已具备团队成员记忆能力，用于辅助任务归属判断：

- 成员别名。
- 负责领域。
- 项目归属。
- 常见缩写含义。
- 近期已确认任务。
- 正向提示和反向提示。

应用场景：

- 会议中只提到简称、别名或项目代号时，辅助识别可能负责人。
- 避免把“参与评审的人”误判为“执行负责人”。
- 根据近期任务和领域归属减少重复确认成本。

### 3.5 飞书任务确认卡片

当前任务卡片支持：

- 按负责人私发任务卡片。
- GetNote 统一发送给统筹人处理。
- 修改任务名称。
- 选择负责人。
- 选择旧任务进展对应的正式总表任务。
- 选择工作类型。
- 修改任务进展说明。
- 单个任务独立提交为新任务。
- 单个任务独立提交为旧任务进展。
- 单个任务独立丢弃。
- 点击某一项后只置灰该任务，其他任务仍可继续处理。
- 已处理任务显示最终结果，避免重复点击。
- 卡片回调校验操作者和消息，避免旧卡片或非本人误操作。

### 3.6 正式任务总表写入

确认后的新任务写入正式任务总表，当前写入或映射字段包括：

- 事务需求名称。
- 需求状态。
- 跟进人。
- 开始日期。
- 完成日期。
- 工作类型。
- 任务进展或进展描述。
- 备注。

新任务默认进入“进行中”状态。若正式总表存在“工作类型”字段，系统写入卡片选择结果；若旧表没有该字段，则跳过，避免因字段不存在导致入表失败。

### 3.7 任务巡检

任务进入正式总表后，系统可以巡检以下问题：

- 进行中任务逾期。
- 进行中任务缺少进度或完成日期。
- 进度已 100% 但状态未完成。
- 状态已完成但进度未 100%。
- 待开始任务已经超过开始日期。
- 明日到期但未完成。
- 多日未有效更新。
- 缺少跟进人。

巡检卡片支持相关人员更新状态、进度评估、开始日期、完成日期和延期说明。进行中的巡检卡片现在可以同时填写开始日期和完成日期。

### 3.8 Resident Worker 和运维接口

系统支持服务内置 resident worker，自动执行：

- 飞书 Wiki / docx 扫描。
- GetNote 扫描。
- 正式任务总表巡检。

同时提供维护接口用于评审、手动补发和排障：

- 手动触发最新 Wiki / docx 和 GetNote 扫描。
- 手动触发单个 GetNote note_id 重跑。
- 查询 GetNote 卡片投递状态。
- 查询 draft 卡片投递状态。
- 强制重发卡片。
- 刷新已发送卡片。
- 成员记忆 CRUD。
- 触发成员近期任务记忆刷新。

## 4. 主要应用场景

### 场景一：每日会议后自动整理任务

适用对象：会议组织者、项目负责人、任务负责人。

原人工流程：

```text
打开会议纪要
  -> 通读全文
  -> 标记任务句子
  -> 判断负责人
  -> 判断是否新任务
  -> 复制到正式任务表
  -> 私下通知负责人确认
```

自动化流程：

```text
会议原文进入指定目录
  -> worker 自动读取
  -> AI 提取任务
  -> 系统生成飞书卡片
  -> 负责人在卡片中确认
  -> 自动写入正式任务表
```

价值：会议结束后任务可以更快进入执行系统，减少人工整理和漏记。

### 场景二：GetNote 无发言人文本统一分配

适用对象：任务统筹人。

GetNote 往往没有可靠发言人，系统不强行猜负责人，而是生成多任务卡片发给统筹人。统筹人逐项修改任务、选择负责人、选择工作类型、提交或丢弃。

价值：既利用 AI 做任务初筛，又保留人工最后确认，降低错误分配风险。

### 场景三：旧任务进展自动归档

适用对象：项目管理人员、任务负责人。

系统识别“已完成、继续推进、测试中、接入总表”等进展表达，并允许在卡片中选择对应旧任务。确认后写入进展，而不是新建重复任务。

价值：减少正式总表中同一事项重复创建，保持任务主线连续。

### 场景四：正式任务巡检

适用对象：管理人员、任务负责人。

系统定期发现逾期、缺完成日期、长期无更新或状态与进度矛盾的任务，通过飞书卡片让负责人补充进度或调整状态。

价值：减少人工翻表检查，让任务维护从“人工巡表”变为“异常驱动”。

### 场景五：评审现场手动演示

适用对象：评审人员、产品负责人、开发人员。

通过维护接口可以在另一台电脑上手动触发一次正式可用卡片发送，便于现场展示：

```text
POST /api/meeting/maintenance/analyze-latest-feishu-wiki-docx
POST /api/meeting/maintenance/sync-getnote
```

请求需携带维护 token，演示时不需要登录服务器。

## 6. 人工耗时和节省时间估算

以下为按常见会议规模估算的参考值，后续可根据真实使用数据持续修正。

| 工作项 | 原人工方式耗时 | Agent / 自动化后耗时 | 单次节省 | 说明 |
|---|---:|---:|---:|---|
| 通读 30-60 分钟会议纪要并找任务 | 20-40 分钟 | 2-5 分钟人工复核 | 15-35 分钟 | AI 自动抽取任务和证据 |
| 整理任务名称和说明 | 10-20 分钟 | 2-5 分钟修改卡片 | 8-15 分钟 | 卡片中只修正必要内容 |
| 判断负责人并逐个通知 | 10-30 分钟 | 1-5 分钟确认或调整 | 9-25 分钟 | 自动按负责人私发或统筹分配 |
| 判断新任务/旧任务进展 | 10-20 分钟 | 2-5 分钟选择旧任务 | 8-15 分钟 | 系统提供历史匹配和旧任务下拉 |
| 录入正式任务总表 | 10-30 分钟 | 0-3 分钟 | 10-27 分钟 | 确认后自动写入 |
| 处理 GetNote 无发言人任务 | 30-60 分钟 | 5-15 分钟 | 20-45 分钟 | 统筹人只处理候选任务卡片 |
| 每日任务巡检 | 30-90 分钟 | 5-15 分钟 | 25-75 分钟 | 系统只推送异常任务 |
| 评审现场准备演示卡片 | 10-20 分钟 | 1-3 分钟 | 9-17 分钟 | 维护接口远程触发 |

按每天 1-3 场会议估算，当前工具可以为任务统筹和项目管理节省约 1-3 小时/天。若会议数量更多或任务表维护频率更高，节省时间会进一步放大。

## 7. 已交付模块说明

### 7.1 飞书 Wiki / docx 会议原文 Worker

功能：自动扫描指定 Wiki 目录下的 docx 会议原文，读取文本并进入任务分析链路。

应用场景：飞书会议智能纪要或人工整理后的会议原文统一放入“会议原文”目录，由 worker 自动处理。

通用能力：目录扫描、内容 hash 去重、失败重试、权限阻断、后台周期执行。

人工节省：每篇文档减少 5-15 分钟查找和手动复制原文时间。

### 7.2 GetNote 同步 Agent

功能：读取 GetNote 最近笔记，筛选当天工作安排类笔记，提取转写文本并生成任务卡片。

应用场景：会议不在飞书智能纪要中沉淀，或临时用 GetNote 记录时。

通用能力：笔记列表扫描、note_id 幂等、内容 hash、最小年龄等待、lookback 窗口、强制重发。

人工节省：每篇笔记减少 10-30 分钟手动复制和初筛时间。

### 7.3 AI 任务提取和过滤 Agent

功能：从会议原文提取主线任务、旧任务进展、负责人候选和证据，并过滤讨论型内容。

应用场景：会议纪要、周报、评审记录、同步会记录。

通用能力：结构化抽取、任务命名优化、主线任务识别、无效任务过滤、候选审计。

人工节省：每场会议减少 20-40 分钟阅读和任务提炼时间。

### 7.4 负责人归属和成员记忆 Agent

功能：维护团队成员领域、别名、项目归属和近期任务，为任务归属和提示词提供上下文。

应用场景：成员经常用简称、项目代号或只说“我这边继续处理”的会议。

通用能力：成员画像、近期任务记忆、别名匹配、领域提示、负向误判提示。

人工节省：每场会议减少 5-15 分钟负责人核对时间，并降低误分配成本。

### 7.5 飞书任务确认卡片 Agent

功能：把待确认任务生成飞书交互卡片，支持修改、分配、工作类型选择、新任务确认、旧任务进展确认和丢弃。

应用场景：任务负责人确认自己的任务，或统筹人处理无负责人任务。

通用能力：卡片表单、下拉选项、按钮回调、消息校验、单项处理、幂等写入。

人工节省：每场会议减少 10-30 分钟逐个通知和收集确认结果时间。

### 7.6 正式任务总表写入 Agent

功能：将已确认任务写入正式总表，并同步状态、负责人、工作类型和日期字段。

应用场景：会议任务进入统一任务管理系统。

通用能力：字段映射、schema 校验、人员字段适配、旧表兼容、失败诊断。

人工节省：每场会议减少 10-30 分钟手动录表时间。

### 7.7 旧任务进展更新 Agent

功能：识别和确认旧任务进展，更新已有正式任务，而不是重复创建新任务。

应用场景：每日站会、周会、项目进展同步。

通用能力：历史任务匹配、旧任务下拉、进展描述写入、状态和进度映射。

人工节省：每场会议减少 5-20 分钟查找旧任务和补进展时间。

### 7.8 正式任务巡检 Agent

功能：定期检查正式总表异常任务，并通过卡片让负责人补充状态、进度、开始日期、完成日期和延期说明。

应用场景：项目管理、任务逾期检查、进展维护。

通用能力：规则巡检、异常分组、负责人卡片、管理汇总、字段更新。

人工节省：每日减少 30-90 分钟人工巡表时间。

补充规则：已完成、已取消任务属于终态任务，不再进入逾期、进度不完整、长期未更新或明日到期提醒。若历史上已经误发巡检卡片，可通过维护接口将对应审计卡片安全收口为“已处理”，不会修改正式任务记录。

### 7.9 运维和评审触发 Agent

功能：提供维护接口和脚本，用于健康检查、成员读取、投递状态查询、失败卡片补发、强制重发、现场演示触发。

应用场景：上线后排障、评审演示、远程手动触发正式卡片。

通用能力：Bearer token 鉴权、脱敏返回、dry-run / execute 安全开关、强制重发保护。

人工节省：每次排障或演示减少 10-30 分钟登录服务器和手工拼流程时间。

## 8. 当前交互卡片能力清单

### 8.1 新任务卡片

支持字段：

- 任务名称。
- 工作类型。
- 负责人。
- 备注或进展说明。

支持操作：

- 标记为新任务。
- 标记为旧任务进展。
- 刷新旧任务候选。
- 丢弃。

### 8.2 GetNote 多任务卡片

支持能力：

- 多任务同卡展示。
- 每个任务独立处理。
- 点击某项后仅该项进入处理中。
- 兄弟任务继续可点击。
- 任务处理完成后显示最终状态。
- 未选择负责人时不执行该项。

### 8.3 任务巡检卡片

支持字段：

- 状态。
- 进度评估。
- 开始日期。
- 完成日期。
- 延期说明。

进行中任务如果需要填写开始日期，也会显示完成日期，方便一次性补齐计划和实际完成信息。

## 9. 数据和安全边界

系统遵循以下原则：

- 不在文档中记录真实 token、app secret、open_id 明文。
- 维护接口使用 Bearer token。
- 健康检查和投递查询只返回脱敏状态。
- 卡片回调校验消息和操作者。
- 强制重发必须显式传 `force` / `execute` 或 `force_card_resend`。
- 权限错误不自动切换到其他身份或其他数据源。

## 10. 运行和验证方式

常用验证命令：

```bash
npm --prefix server test
npm --prefix server run test:feishu-task-cards
npm --prefix server run test:getnote-workflow
npm --prefix server run test:master-task-audit-cards
npm --prefix server run test:master-task-audit-actions
npm --prefix server run test:member-memory
```

常用运维接口：

```text
GET  /api/health
POST /api/meeting/maintenance/analyze-latest-feishu-wiki-docx
POST /api/meeting/maintenance/sync-getnote
GET  /api/meeting/getnote-card-deliveries/:noteId
GET  /api/meeting/draft-card-deliveries/:draftId
POST /api/meeting/force-resend-draft-task-card
POST /api/meeting/refresh-draft-task-cards
POST /api/meeting/maintenance/master-task-audit-cards/:auditLogId/close
```

关闭误发巡检卡片时需要维护 Bearer Token 和关闭原因。接口会先确认正式总表任务当前状态为“已完成”或“已取消”，然后只更新巡检审计记录并将原卡片改为“任务巡检已处理”。

以后新增任何 Agent、Skill、Worker、维护脚本或有效交付功能，都必须在本文增加一节，至少包含以下内容：

```text
### 模块名称

功能：说明这个 Agent / Skill / Worker 做什么。

应用场景：说明什么情况下使用。

通用能力：说明是否可复用于其他工具或流程。

输入：说明依赖哪些数据、接口、配置或人工动作。

输出：说明产出什么结果，写到哪里，发给谁。

节省时间：给出单次节省和每日/每周估算。

风险和边界：说明哪些情况不能自动处理，哪些需要人工确认。

验证方式：说明对应测试、接口或演示步骤。
```

文档更新规则：

1. 新 Agent 没有文档，不能视为完整交付。
2. 有效交付如果之前没写，需要在下一次迭代时补齐。
3. 已有文档如果和最新功能不一致，需要同步修订。
4. 时间节省估算可以先给区间，后续用真实数据更新。
5. 文档不能包含真实 token、secret、open_id、完整 message_id。

## 12. 后续可补充方向

- 按真实使用统计更新每类场景平均节省时间。
- 增加每周自动化处理会议数量、任务数量和确认率统计。
- 增加 GetNote 任务误判样本库，持续优化主线任务识别。
- 增加工作类型识别准确率统计。
- 增加巡检卡片处理时效统计。
- 将常用评审演示命令整理成单独 checklist。
- 为新增 Agent / Skill 建立固定文档模板和验收清单。

## 13. 管理层摘要

当前工具已经形成从会议内容到任务执行跟进的自动化闭环。它能自动读取会议原文，提取可执行任务，过滤无效内容，判断新旧任务，生成飞书确认卡片，写入正式任务总表，并通过任务巡检持续跟踪任务状态。

从人工处理角度看，过去一场会议通常需要 40-120 分钟完成阅读、整理、分配、录表和通知；现在多数工作由 Agent 和 Worker 自动完成，人工主要集中在卡片确认和必要修正，通常可压缩到 5-20 分钟。按每天 1-3 场会议估算，可节省约 1-3 小时人工整理和任务维护时间。

后续重点不只是继续开发功能，也要同步沉淀每个 Agent / Skill 的开发文档，让每次有效交付都能说明“做了什么、用在什么场景、能复用什么能力、原本人工要多久、自动化后节省多少时间”。
